# CON-30 — Travel provider feasibility

Verified on **6 October 2026** against official provider material. Implementation baseline: `origin/main` at `a243ba1` (CON-29, PR #6). [CON-29](https://linear.app/concert-app67/issue/CON-29/define-trip-intelligence-v1-product-spec) defines the product; [CON-30](https://linear.app/concert-app67/issue/CON-30/research-travel-providers-for-trip-intelligence-v1) tracks this research.

## Decision

**Stop before integration code.** The project owner confirmed that Encore currently has no production transport access. No authenticated journey, account quota, or permission to retain provider results was verified for this project. This is an access prerequisite, not a claim that all travel APIs are unavailable.

**Recommended smallest follow-up: SNCF train schedules first**, after receiving a developer token and retrieving the applicable API terms. Show actual journeys for near-term concerts, with transport price, seat availability and total trip cost unknown. Confirm France and each intended international route with authenticated searches before advertising coverage. SNCF Connect is a separate commercial price API.

For priced European travel with external checkout, **Omio Meta Search is the preferred partner contact**. Start with trains if approved; do not implement flights and buses simultaneously. Public partner descriptions do not establish access, response schemas or caching rights for Encore.

No accounts were created, contracts accepted, provider contact messages sent, bookings made, or travel inventory scraped. No integration, secret, environment variable or production setting is added by this research.

## Evidence and limits of verification

- The public SNCF API returned **HTTP 401** to an unauthenticated `GET https://api.sncf.com/v1/coverage`; the JSON message requires a token. This proves the endpoint responds, **not** token issuance, accessible coverage or successful journeys. The token request form is visible; it was not submitted. Both published terms paths were inaccessible during this investigation. Do not label the SNCF API discontinued or its key unobtainable.
- The rendered [Amadeus portal](https://developers.amadeus.com/) explicitly says its Self-Service portal was decommissioned on 17 July. Static search still returns old API pages. Current portal status takes precedence; the research date is after July 2026.
- `https://navitia.io/` opened Hove's corporate site. [Navitia docs](https://doc.navitia.io/) still describe technical fields and tell developers to request a token from their transport authority. This does not prove that all hosted instances are closed, or that old free registration still works.
- Rome2Rio's historical reference was available as an indexed official excerpt; direct retrieval failed. No official current new-developer onboarding was verified. Do not assert a shutdown date from third-party articles.
- The local `.env.local`, `.env.example` and process variable names checked for SNCF, Navitia, Amadeus, Trainline, Omio and Duffel contained no configured transport credentials. Values were not printed. The owner separately confirmed no current production transport access. Remote deployment secrets and private partner accounts were not inspected.
- No authenticated provider search was made; actual European route coverage, field completeness, account quotas and project-specific permissions remain access acceptance checks.

## Existing architecture and changes needed after access

Reviewed the merged `src/server/providers/travel-sample.ts`, `src/server/trips.ts`, `src/domain/trip-types.ts`, `src/domain/trip-scoring.ts`, trip API/save routes, `src/server/schema.ts`, migrations, `src/server/data.ts`, `src/components/trips-screen.tsx`, environment templates and trip/domain/browser tests. This document does not change their behaviour.

The integration belongs behind **`TransportProvider.getOptions`** in `src/domain/trip-types.ts`, using a server adapter in `src/server/providers`. The older `TravelProvider.search` in `src/domain/types.ts` is not the abstraction used by the merged Trip Intelligence planner. Reuse bounded, uncached HTTP requests and sanitised errors; do not expose tokens to clients.

The following are implementation requirements, not claims of existing safeguards:

1. Select sample providers only for explicit sample/demo mode or deterministic tests/local development. Currently `generateTripOptions` defaults to sample transport and accommodation for every call, including live users. An outage, missing key, unsupported date or route must produce a clear unavailable state, never fictional live inventory.
2. Preserve source, provider identity, optional external journey ID, mode, actual stop/place identities, departure, **arrival**, duration, transfers when supplied, observation time, currency/price semantics, validated link and availability meaning. Current `TransportOption` lacks arrival, external ID and availability, and requires `returnAt`. A one-way journey must not acquire a fabricated return; a real return needs a separate query. Honour provider coverage timezone, event timezone and DST; do not append `Z` to local times.
3. Accommodation is still fictional. Current pairing returns no options when no stays exist. A real timetable integration needs an explicit “stay not connected” representation, without invented hotel names, rates or distance. Unknown stay or transport prices keep `estimatedTotal` null. Do not pair live journeys with sample hotels silently.
4. Keep the deterministic 40% music / 35% convenience / 25% cost formula and comparison-label rules. Unknown inputs must not create unsupported “Cheapest”, “Fastest”, “Easiest” or “Best value” claims. Validate currency codes and compare like-for-like price scope; no currency conversion or borrowing fares from another provider.
5. Apply freshness on generation, every saved-trip read (`getAppData` and `/api/trips/saved`) and while a planner stays open. Current saved trips are unfiltered JSON snapshots; current save validation accepts arbitrary transport/accommodation objects. Validate server-side source, link, event and ownership; avoid persisting provider content unless the licence permits it.

### Proposed freshness and fallback rules

After access terms are verified, initially use **no persistent provider-response cache**. Requery when opening/reopening a plan; save user intent and route references only where permitted. A suggested application display ceiling is **5 minutes** for a schedule observation, shortened by provider limits and data validity. This is a proposed conservative product rule, **not an SNCF contractual TTL or storage permission**.

For a future priced provider, hide price and any dependent total once the earliest of provider expiry, agreed freshness limit and application ceiling is reached. Invalid/missing/future observation timestamps invalidate a quote. Keep attribution with the observation; invalidate availability separately from timetable existence. An expired saved plan remains a plan, not a current offer. Only accept documented HTTPS provider/checkout hosts; generic homepages and invented search URLs are not offer deeplinks.

For SNCF schedules, price/currency and seat availability remain unknown and there is no booking-offer button. Show “SNCF timetable — price and seats not provided”; distinguish scheduled from real-time journeys. Dates outside the authorised dataset window, ambiguous station matches, outages and exhausted quotas return unavailable. Existing sample mode remains explicitly fictional. These rules are proposed for the follow-up and are not implemented here.

## Access path and smallest follow-up issue

Access acceptance criteria:

- Owner requests a token through the [official SNCF form](https://numerique.sncf.com/startup/api/token-developpeur/) and obtains the current API terms through [SNCF support](https://numerique.sncf.com/faq/api/) if the licence links remain broken. Confirm commercial concert planning, attribution and saved-plan retention. Put the token only in ignored local/hosting secrets.
- With that authorised token, verify coverage, dataset validity and searches for Paris–Lyon, Paris–Brussels and Paris–Amsterdam on supported dates. International failures narrow the advertised scope to verified routes; do not assume operator names imply complete Europe coverage.
- Capture permitted, redacted journey fixtures and the actual field/timezone schema. Confirm account limits. Only then add the necessary server configuration, one train adapter, sample/live separation, unknown stay UX and saved-plan freshness handling.
- Add parsing/malformed payload, missing fare, invalid currency, stale/future observations, timezones/DST, missing return, outage/quota and unsupported-date cases, generation with realistic fixtures, malicious link/save validation, and sample/live isolation tests. Run lint, typecheck, unit tests, build and focused planner/save/reopen/expiry Playwright flows.

If real fares and cross-border checkout are required before a schedule-only release, contact [Omio B2B](https://www.omio.com/corporate/omio-b2b/) specifically for **Meta Search with external checkout**. Request sandbox/production credentials, schema, France/nearby-Europe rail inventory, price scope/fees/currency, availability semantics, deeplink hosts, quotas, API charges, attribution and cache/retention rights. Affiliate signup is not enough. SNCF Connect's published partnership contact is `DL_PARTENARIATSMKG@connect-tech.sncf`; FlixBus distribution uses `online-distribution@flixbus.com`. No outreach has been sent.

Hotels, flights, buses, native checkout and affiliation tracking remain later work. Neither a three-provider integration nor an API-shaped mock is a substitute for access validation.
