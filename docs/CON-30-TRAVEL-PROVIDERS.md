## Corrected conclusion

**Encore must compare realistic concert journeys across trains, flights and buses/coaches, without a default preference for any mode, operator or data provider.** SNCF, Eurostar, Trenitalia, FlixBus, airlines and other European operators compete on journey merits. Selecting an API does not give its operators a ranking advantage.

**Omio Meta Search is the leading candidate to validate.** Its official B2B description covers all three modes, real-time pricing, availability, routing and redirection to Omio or branded checkout. This is the closest documented fit for native comparison without Encore processing bookings/payments. Its separate Booking API lets partners manage the transaction as merchant of record. [Omio B2B](https://www.omio.com/corporate/omio-b2b/).

This is a conditional recommendation, **not a verified live integration**. Exact schemas, route/operator entitlements, fees, quotas, freshness, retention and Encore's eligibility remain unverified. The owner confirmed **no current production transport access**. Keep PR #7 research-only; obtain approved multimodal access before runtime work.

**SNCF's information API is only a possible supplemental timetable source.** It cannot establish commercial fares, seat availability or offer checkout. Easier token access is not a reason for an SNCF-only release or a replacement for the primary multimodal objective. [SNCF FAQ](https://numerique.sncf.com/faq/api/).

## Target architecture: provider-neutral TransportProvider

These are follow-up requirements, **not runtime changes made by CON-30**. Retain `TransportProvider` in `src/domain/trip-types.ts`, with server adapters in `src/server/providers`; the older `TravelProvider.search` is not used by the merged planner.

A concert-trip request carries origin/destination identities, dates/windows, event timezone/start, return requirements and passenger/fare scope. An orchestrator queries every configured authorised provider with bounded timeouts and combines normalized offers. Multiple providers can contribute to the same trip; one can supply several modes. Failures produce attributed partial results, with no source priority.

The option contract supports these semantic fields (existing camelCase naming may remain). **Missing source data stays null/absent, never fabricated.**

| Field                       | Semantics                                                                                                                                                                               |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `provider`                  | Search/data source, with attribution and sample/live provenance; distinct from operator.                                                                                                |
| `operator/carrier`          | Operating company as supplied, per segment if multiple.                                                                                                                                 |
| `mode`                      | `train \| flight \| bus` from documented source data. Mixed-mode legs explicit, never relabelled as one mode.                                                                           |
| `external journey/offer ID` | Preserve supplied IDs, scoped to provider; absent if not exposed. Local identity remains labelled local.                                                                                |
| `origin / destination`      | Actual station/airport/stop identities and locations where supplied, alongside city intent.                                                                                             |
| `departure / arrival`       | Source timestamps with documented timezone/offset; never append `Z` to local times.                                                                                                     |
| `duration`                  | Journey elapsed duration including transfer waits, supplied or explicitly derived from validated timestamps; retain coverage basis.                                                     |
| `transfer count`            | Supplied or documented derivation from complete legs; unknown is not zero.                                                                                                              |
| `price / currency`          | Nullable exact decimal/minor-unit amount, supported validated currency, passengers/direction/fees/service scope and completeness. “From”, indicative and partial fares remain distinct. |
| `availability semantics`    | Preserve documented state and observation: scheduled-only, bookable as observed, unavailable or unknown. Price/search presence does not guarantee a seat; count only if supplied.       |
| `booking/deeplink URL`      | Documented offer checkout link with validated HTTPS host; absent if unsupported. Generic homepage is not an offer deeplink.                                                             |
| `observed_at`               | Server observation and upstream timestamp if supplied; reading an old result does not renew it.                                                                                         |
| `provider expiry`           | Actual expiry if exposed, separately for fare, availability/checkout as needed; absence is unknown, not unlimited validity.                                                             |

Do not combine one source's fare with another's availability. Deduplicate only when provider-scoped IDs establish identity; retain distinct commercial offers and stable IDs for several offers of one mode. Do not stitch separately priced legs into a supposedly complete, protected ticket; retain separate checkout obligations. A complete provider-priced journey can contain multiple operators/modes.

Query returns separately or preserve an actual round-trip offer. Current mandatory `returnAt` cannot justify inventing a return. Concert compatibility requires venue arrival, including known terminal-to-venue travel and an explicit buffer. Return feasibility requires an actual departure after event end plus venue-to-terminal/boarding time. Unknown event end, access travel, timezone or return timing means **unknown feasibility**. Declared planning assumptions remain separate from provider facts.

## Deterministic ranking

Rank eligible options for the **same concert and comparable request**. Total price, departure/arrival, duration, transfers, concert compatibility, return feasibility, availability, checkout and freshness are first-class inputs. Provider/operator/mode names and affiliate commissions have **zero ranking weight**.

1. **Comparison scope:** reject confirmed unavailable/impossible/concert-incompatible journeys from recommended attendance plans. Incomplete records can remain visible with missing data stated. Cohorts use the same passengers, directions, baggage/required fees and service basis. One-way quotes cannot compete as complete return totals. Compare equal supported validated currencies; initially EUR, without invented FX.
2. **Cheapest:** lowest comparable complete, valid, fresh total. Transport labels use all required travel components and both directions when requested. Whole-trip labels require ticket + transport + required stay/access costs, all fresh and same-currency. Unknown costs are not zero. Exclude partial, indicative, “from” and stale prices.
3. **Fastest:** shortest complete total travel duration on the same basis, including transfers/waits and both legs for return requests. Do not compare airport-to-airport flight time with door-to-venue rail time. Missing access/boarding duration withholds the overall label; supplied journey duration can be shown separately. No price required for duration-only ranking.
4. **Easiest:** highest deterministic convenience score from transfers, departure/arrival timing, arrival buffer, return feasibility and total duration. Require these inputs on a comparable basis; unknown inputs cannot earn points. Infeasible attendance/return is excluded before scoring.
5. **Best value:** highest combined price + convenience score, only with at least two complete, fresh, same-currency comparable offers qualifying for convenience scoring. No singleton/unknown-price/neutral fallback gets this label. Concert music-fit ranking is separate.

Proposed versioned convenience policy (product choices, not provider facts):
`C = 100 × (0.25 T + 0.20 H + 0.20 B + 0.20 R + 0.15 D)`.
`T = 1/(1 + totalTransfers)`;
`H` = fraction of outbound/return departure/arrival times inside declared acceptable travel hours;
`B = clamp(venueArrivalBuffer/preferredBuffer, 0, 1)`;
`R = 1` for a verified return inside the requested window;
`D = 1/(1 + totalTravelMinutes/120)`.
Proposed 60-minute preferred concert buffer and 07:00–23:00 acceptable hours are visible, configurable planning defaults applied in the relevant local timezones, equally across modes. Boarding/check-in requirements must be documented or explicit planning inputs, not invented provider values. Missing prerequisites make `C` unavailable. An explicit one-way request has no return requirement; set `R = 1` as a policy neutral value and compare only within that one-way cohort, without claiming a feasible return.

Within a qualifying cohort, `P = 100 × (maxTotal - total)/(maxTotal - minTotal)`, or `P = 50` for equal totals; proposed `V = 0.5 P + 0.5 C`. Compute without intermediate rounding; display rounded scores, policy version, inputs and reasons.

Comparative labels require at least two eligible comparable options. Equal metrics are ties, not unique winners; show a tie or omit a unique badge. Display ties deterministically by departure, arrival and stable identity, without interpreting order as a provider preference. State the cohort and excluded/missing data.

**Never compare** stale prices, unsupported different currencies, incomplete quotes as complete, or samples with live offers. Timetable-only results cannot enter priced cohorts or refresh a commercial quote.

## Freshness, fallback and existing gaps

Use the approved provider's actual refresh/expiry terms. Start without persistent response caching unless allowed. Proposed application quote ceiling: **5 minutes**, shortened by provider expiry, contractual limits and upstream validity. This is a product policy to validate before release, not a provider guarantee or cache licence.

Apply freshness at generation, in open planner views and on every saved-plan read. Expire price/dependent totals, availability and checkout independently as needed. Missing/invalid/future observation times invalidate quotes. Saved intent is not current inventory; requery authorised sources and retain only permitted content/references. External checkout can reprice and no displayed offer reserves a seat.

Missing access, unsupported routes/dates, quotas or outages produce attributed partial/unavailable results. Retain only other valid authorised offers; all-source failure gives no live recommendation. Never replace failures with samples, stale quotes, invented availability or an SNCF-only “multimodal success”. Label schedule supplements clearly.

Reviewed merged provider, generation/scoring, API/save/read routes, schema, UI and tests. Follow-up gaps:

- `generateTripOptions` defaults to fictional transport/stays for every call. Enforce sample/live isolation, including saved trips; missing live credentials cannot select samples.
- Current `TransportOption` lacks arrival, external IDs, availability and expiry, with required `returnAt`. Change its contract only against approved payloads.
- Current orchestration uses one provider, pairs offers with fictional hotels and requires stays. Accept multiple sources and explicit unknown/not-required stays without invented names/prices/distances.
- Current convenience omits event timing/return feasibility. Existing overall formula (40% music / 35% convenience / 25% cost) can yield Best value without comparable prices. The transport rules above supersede the prior instruction to preserve that formula for transport Best value; concert ranking remains a separate concern.
- Saved JSON snapshots and arbitrary transport/accommodation save objects need server validation of source, ownership, event, link, scope and freshness. Snapshot retention cannot be assumed licensed.
