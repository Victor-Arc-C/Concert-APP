# CON-31 — Accommodation providers for Trip Intelligence v1

Research checked against official public material on **6 October 2026**. Base: current `origin/main`, `a243ba1e51b44864b7d8a88497a0a430aa436860` (CON-29 / PR #6). The owner confirms **no approved accommodation API access**, including test access. No API credentials, reservations, applications or partner communications were used or submitted.

## Decision

**Keep CON-31 research-only. Make Nuitée LiteAPI / Nuitee Connect the first access-validation candidate for this new project.** It documents free account/sandbox-key onboarding, current hotel rates, city/coordinate search and a hosted white-label checkout that can accept a selected offer ID. That is a more concrete initial access path than managed-only programs. This is a conditional recommendation: Encore has no account/key, production configuration, confirmed French/European inventory or approved content/comparison rights. No signup or payment setup was performed. [LiteAPI key onboarding](https://docs.liteapi.travel/docs/getting-a-sandbox-key), [hotel rates](https://docs.liteapi.travel/reference/post_hotels-rates), [selected-offer checkout](https://docs.liteapi.travel/docs/deeplinking-to-whitelabel).

**Booking.com Demand “Search, look and redirect” remains the preferred managed affiliate alternative; Agoda Online Affiliates/MSE is another explicit native-comparison/redirect model.** Booking.com requires a managed contract/account manager; ordinary affiliate registration is not Demand approval. Agoda requires commercial onboarding/certification. Neither publishes guaranteed new-project API acceptance. If LiteAPI's rights, fee completeness or hosted checkout fail validation, choose an approved redirect partnership rather than implementing speculative booking infrastructure. [Booking prerequisites](https://developers.booking.com/demand/docs/getting-started/prerequisites), [Demand overview](https://developers.booking.com/demand/docs/getting-started/overview), [Agoda models](https://developer.agoda.com/demand/docs/getting-started).

No researched provider is currently usable **by this project**. Public documentation, sandbox examples, affiliate links and a shared demonstration key do not satisfy the implementation gate. Do not add speculative adapters, environment variables or production sample hotels. Approval, useful licensed inventory and a verified checkout flow must precede runtime work.

Duffel Stays is the next API candidate: its search/quote data is useful and developer onboarding is clear. However, access must be requested, and the documented hosted Links accommodation search does not establish that an already selected native rate can be handed to the same checkout. Expedia Rapid, Hotelbeds and Travelgate are distribution/booking integrations with more operational and contractual work than v1's external checkout needs. Trip.com has a documented hotel redirect response, but current new-project access and content rights remain unverified. [Duffel onboarding](https://duffel.com/docs/guides/getting-started-with-stays), [Duffel Links](https://duffel.com/docs/guides/duffel-links).

Two otherwise promising alternatives are unavailable to new API applicants today: **Expedia Travel Redirect** pauses applications; **Stay22 DirectTravel** pauses sign-ups while replacing its API. Stay22's event-oriented Maps widget is a different product, not native structured offers for Encore's rankings. Amadeus's current developer portal does not offer the former Self-Service onboarding route; do not infer current Hotels access from historical tutorials. [Travel Redirect](https://developers.expediagroup.com/xap-apis), [Stay22 API notice](https://dev.stay22.com/docs/api), [Stay22 Maps](https://dev.stay22.com/docs/maps), [Amadeus portal](https://developers.amadeus.com/).

Transport remains provider-neutral and multimodal. CON-30's corrected strategy is in [PR #7](https://github.com/Victor-Arc-C/Concert-APP/pull/7), which is separate and unmerged at this research base. Missing accommodation must not create a fictional hotel component in a transport trip.

## Current implementation audit

This is an audit of main, not a runtime change:

- `src/server/providers/travel-sample.ts` synthesizes two hotel names, prices and venue distances per city, a one-night stay and a generic Booking.com URL. These are fictional; `observedAt` records sample generation, not an inventory observation.
- `src/server/trips.ts` defaults to sample transport and accommodation without an explicit production/live gate. Live concert selection does not make these stay offers real. It fixes one guest/one night and pairs options by array position; it returns no itineraries when either provider supplies no options.
- `src/domain/trip-types.ts` already has a neutral `AccommodationProvider`, but lacks external property IDs, property coordinates, room/child-age semantics, availability, rating rights, provider expiry and price/fee scope. `Concert` has city/venue names without venue coordinates; city-centre coordinates are insufficient for “Closest.”
- `src/domain/trip-scoring.ts` can assign Best value using neutral missing-cost scoring and sample distances. It does not enforce current comparable accommodation quotes or comparable review scores. The existing overall trip score is not the proposed hotel Best value rule.
- `src/server/api.ts` accepts trip snapshot components with `z.any()`; `src/server/data.ts` and saved-trip reads return stored JSON without revalidation. `src/components/trips-screen.tsx` displays one-night prices/distances and opens supplied hotel URLs. Saved snapshots have no implemented inventory expiry or approved hotel-host policy.

**The current runtime therefore does not enforce the requested production sample/live separation.** No approved hotel provider is connected. This PR does not fix that runtime behavior because the user explicitly requires stopping runtime implementation when access is unavailable. ## Provider-neutral target contract

Extend the existing server-side `AccommodationProvider` only after access is approved. Inputs should include destination/venue coordinates when reliable, local check-in/check-out dates, room occupancy (adults and child ages per room), supported currency and request time. Dates must be derived from the concert/travel plan and property timezone; do not always assume one night or check-in at a fictional UTC hour.

Preserve these concepts, with unknown/absent values when the source does not expose them:

| Concept                                                     | Mapping rule                                                                                                                                                                               |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Provider, external property ID/name, external offer/rate ID | Keep provenance separate from the property/operator; preserve offer ID only if supplied. IDs are scoped to provider, not deduped by name.                                                  |
| Latitude/longitude                                          | Reliable licensed property coordinates; separate venue coordinates and their provenance. No fabricated city offsets.                                                                       |
| Local check-in/check-out, occupancy                         | Exact requested stay and provider-returned scope. Reject mismatches.                                                                                                                       |
| Total-stay amount/currency                                  | Decimal-safe amount, complete room/guest/night scope, response currency, tax/fee inclusions and payable-at-property components. Keep nightly/display/net prices as distinct facts.         |
| Availability                                                | Available-at-observation, unavailable, unknown; never turn omitted stock into available or convert a search result into a guarantee. Quantity only if explicitly supplied and trustworthy. |
| Rating                                                      | Distinguish guest review score/scale/count from hotel stars. Include source and approved display permission; omit if unlicensed.                                                           |
| Image                                                       | Optional approved content only; no implementation needed for first integration if rights are unclear.                                                                                      |
| Booking/deeplink                                            | Provider-supplied, validated HTTPS browser URL for the offered property/date/occupancy. A generic homepage or an authenticated API operation is insufficient.                              |
| `observed_at`, provider expiry                              | Server receipt time plus genuine provider timestamps/expiry if supplied. Missing expiry stays missing; an app revalidation deadline is a different field.                                  |

Several providers can contribute options to the same concert trip. Rank comparable stays independently of transport, then combine feasible stay dates with the multimodal transport options. Do not create hotel costs or complete trip totals when a quote is missing. If transport is real but accommodation unavailable, keep useful transport with an explicit unavailable accommodation state, no hotel Best value or fabricated distance.

### Deterministic curation

Use at most three useful properties, deduplicating labels attached to the same validated offer. Deterministic ties use total amount/distance where applicable, then provider and external property/offer ID, never affiliate commission or operator preference.

- **Cheapest:** minimum comparable current complete total stay in the same supported response currency, dates, occupancy and comparable room/board/cancellation scope. Include mandatory known fees, including payable locally. If complete totals cannot be established, show the partial price as such without this label. Require at least two comparable candidates for a comparative badge.
- **Closest:** minimum Haversine straight-line distance between reliable venue and property coordinates. Display “straight-line distance to venue”; never walking time/distance. Missing either coordinate means no distance or Closest badge. Compare only usable current stay candidates, not sold-out property content.
- **Best value:** require at least two candidates with comparable complete current prices, reliable venue distances, and licensed guest reviews on the same scale/source. Proposed versioned score: `0.45 × priceBenefit + 0.35 × proximityBenefit + 0.20 × reviewBenefit`, each in [0,1]. Price/proximity benefit = `1 - (value - min)/(max - min)` across the eligible set; identical values use 0.5. Review benefit = score divided by its documented maximum only for a compatible zero-based scale. A different scale needs an explicit validated mapping. Different review sources/star categories, missing fields or insufficient candidates suppress the badge. This proposed policy needs validation after access; it is not implemented.

No silent FX: separate currency groups or suppress cross-currency comparisons. Provider conversions must retain their explicit source/rate/time and approved price semantics; supporting them is beyond the first integration. Never compare sample fixtures with live offers. A single complete hotel quote can be shown without claiming it is cheapest or best value.

### Freshness, saved trips and failures

Provider rules override app convenience. Booking.com's public production guide forbids storing dynamic price/availability; do not persist those fields in `saved_trips` or reuse a five-minute cache as an assumed exception. Save licensed identity/search intent and re-query current data on reopen. Static content retention is a separate contract decision.

For a provider that permits short-lived retention, expiry is the earlier of provider expiry and an explicitly configured app revalidation deadline. A suggested **five-minute maximum is an app proposal, not a provider guarantee or permission**; use no cache if terms are stricter or unknown. `observed_at` alone cannot prove availability now. Expired quotes lose current-price/comparison status and checkout eligibility until revalidated. If expiry is not exposed, do not invent it; re-query according to the approved contract.

Reopening a saved trip must revalidate stay intent, current offer, concert status, dates and checkout URL before showing current inventory. On provider outage, zero results, sold-out rate or malformed response, return an explicit unavailable/unknown state. Production must never substitute fictional hotels, totals or coordinates. Existing old snapshots require validation/redaction before display; old arbitrary JSON is not trusted provider data.

Sample providers may run only in tests, explicit local development or explicit demo/sample mode, with visible fictional labeling. Production users and live provider flows must not receive samples. Missing credentials disable that provider rather than enabling fixtures. Validate documented provider/checkout host allowlists server-side: HTTPS only, no embedded credentials, lookalike hosts, arbitrary redirects or API-operation URLs. Confirm exact hosts after approval, not from a guessed affiliate domain.
