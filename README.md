# Encore

A founder-testable, artist-first concert discovery pilot. Start with the [MVP scope, journey and launch metrics](docs/MVP_SCOPE.md); [PRODUCT_AND_TECHNICAL_PLAN.md](PRODUCT_AND_TECHNICAL_PLAN.md) provides background research.

## Run locally

Requires Node 22+ and npm.

```sh
nvm use # or install Node 22 yourself
npm ci
cp .env.example .env.local
npm run dev
```

Open **http://127.0.0.1:3000**. Browse the sample profile or create an account, select artists and set travel preferences. No external account or key is required. Use a test email and a unique passphrase of at least 12 characters. Accounts are local and email ownership is not verified in this closed pilot.

The app creates a persistent PostgreSQL-compatible PGlite database in `.data/encore`. Stop the dev server before running `npm start`; do not open the local database from two processes. Data persists across restarts. For a disposable test environment set `LOCAL_DATABASE_PATH` to a separate folder. Never use local PGlite on Vercel or another ephemeral/multi-process host.

```sh
npm run check
npm run build
npm start
```

To run browser tests with a running app:

```sh
npx playwright install chromium
npm run test:e2e
```

Tests create and delete accounts using `example.test` addresses. Provider integration tests are deterministic and do not need keys. E2E tests expect the default unconfigured-provider state.

## What is implemented

- Landing, signup/login, artist and travel onboarding, responsive personalised feed.
- Persisted saved/dismissed concerts, artist favourites/hiding, pre-tour must-see intentions with cities, ticket budget and quantity.
- Concert detail, same-artist city comparison, qualitative recommendation explanations and filters.
- In-app alerts, preferences, profile data export, disconnect and account deletion.
- Explicit sample/live mode, Ticketmaster search and import, conservative deduplication, raw source mappings, validated outbound ticket links.
- Gated Spotify OAuth with state + PKCE, encrypted tokens, refresh and transient artist-name import for explicit confirmation.
- Consent-gated analytics event storage, SQL migrations, authentication and critical domain tests.

## Boundaries

**All sample concerts, dates and prices are fictional.** They are not real inventory. Photography provides generic atmosphere and does not depict the artist/event named. Sample mode cannot open ticket checkout.

No live transport or hotel provider is connected. Trip Intelligence currently generates fictional sample transport and stays; its provider selection does not yet enforce sample/live separation. No tickets are held, purchased or guaranteed. In-app alerts are evaluated after scheduled refreshes and on app reads; email/push delivery is not connected. Live listings are cached per artist for one hour. Optional local automatic checks run while the server is awake; they are not real-time inventory monitoring.

The [CON-31 accommodation research](docs/CON-31-ACCOMMODATION-PROVIDERS.md) recommends validating Nuitée LiteAPI access first, with Booking.com Demand redirect and Agoda MSE as managed alternatives. No accommodation access is currently available, so this research adds no runtime integration. Production sample gating, licensed content, current complete stay prices and saved-trip revalidation remain prerequisites for that follow-up.

No affiliate commissions, premium subscription, sponsored placement, payment or package checkout is active. Stored ticket clicks are not purchases. Analytics events are collected only after the user opts in; not-yet-implemented actions do not produce fake events.

## Configure live concerts

1. Copy `.env.example` to `.env.local`.
2. Add a legitimate `TICKETMASTER_API_KEY` and restart the server.
3. In **Your artists**, search the live catalogue and follow the exact attraction record. Sample artists deliberately are not automatically matched by name.
4. In **Settings → Concert data**, choose Live Ticketmaster listings and refresh.
5. Check coverage with your intended pilot artists. Unknown prices stay unknown. Source price ranges can exclude fees and are not an inventory guarantee.

Artist searches and event fetches share a conservative database-backed rate limiter. Large tours are capped at five pages/500 returned events per artist in this pilot. Provider errors remain visible; live data never silently falls back to fixtures. The adapter does not retry large jobs indefinitely.

## Spotify gate

Do not enable Spotify based only on having an API key. The current developer policy and quota rules may block this exact business use. Obtain approval first; see the research document.

After approval: set `SPOTIFY_APPROVED=true`, client ID/secret, and `TOKEN_ENCRYPTION_KEY` generated by `openssl rand -base64 32`. Register the exact callback `${APP_URL}/api/spotify/callback`; the default is `http://127.0.0.1:3000/api/spotify/callback`. Use an allowlisted account. In production use an HTTPS origin. Only `user-top-read` is requested. Imported names are transient, require explicit selection and are not converted into derived listening metrics. Disconnect deletes stored tokens. Test real consent, denial, revocation and refresh with an approved account before promising this integration to users.

## Deployment / scheduling

Set `DATABASE_URL` to managed PostgreSQL and set a canonical HTTPS `APP_URL`. The schema is versioned in `src/server/schema.ts`; migrations are applied once during database initialization. Run a single instance first to initialise a new managed database before scaling replicas. This pilot does not yet ship a production migration CLI or distributed ingestion queue.

Set a random `CRON_SECRET` (`openssl rand -hex 32`) and invoke `POST /api/jobs` with `Authorization: Bearer <secret>` from a scheduler. It refreshes followed live artists before evaluating alerts and removes expired sessions/OAuth attempts, old analytics (>30 days), and old rate-limit buckets. Run one scheduled worker centrally before a wider pilot; in-process serialization is not a distributed lock. Without scheduling, analytics cleanup is not automatic. In-app alert delivery is idempotent via a unique user/event/kind constraint.

Database credentials, OAuth tokens and provider keys stay on the server. Do not prefix them with `NEXT_PUBLIC_`. No real secrets are included. A `.env.example` documents settings.

## Private beta invite codes (CON-35)

Set `BETA_INVITE_CODES` (comma-separated, case-sensitive) to require one of those codes at signup. Leave it empty for open signup. Codes are compared server-side in constant time, checked before any account lookup, rate-limited, and never logged or returned. Sign-in for existing accounts is not affected. To rotate a code, change the variable and redeploy.

## Public-launch gates

- Email verification, recovery flow, abuse protections, operational monitoring and external security review.
- Managed DB backups and a defined restore/deletion policy; TLS at the hosting boundary.
- Signed provider permissions, cache/retention review, source attribution and affiliate agreements.
- Final privacy notice: controller identity, contact, legal bases, retention and processor locations.
- Production CSP nonce/hashes replacing the development-compatible inline/eval allowances.
- Managed database and actual provider-account smoke tests, mail/push delivery if offered, and country-by-country coverage checks.
- No package travel or combined checkout until the applicable EU/French rules and 2026 transition dates have been reviewed.

- `src/server/providers`: timeout/error boundary, Ticketmaster, gated Spotify.

## Environments

`APP_ENV` controls data/configuration policy independently of Next.js `NODE_ENV`. Running a local production build with `npm start` does not mean it is a public production deployment.

| Profile | Configuration | Database | Automatic checks |
| --- | --- | --- | --- |
| local (default) | `.env.local`, copied from `.env.example` | Existing `.data/encore`, or `LOCAL_DATABASE_PATH` | Opt-in local timer |
| development | `.env.development.local`, copied from `config/environments/development.env.example` | Separate `.data/encore-development` by default; use separate credentials for a shared dev DB | Opt-in only with local PGlite |
| test / CI | Process environment from `config/environments/test.env.example` or the workflow | Disposable `.data/encore-test` / `.data/encore-ci` | Disabled; live providers and managed DB connections rejected |
| production | Hosting-platform secrets, based on `config/environments/production.env.example` | Required managed PostgreSQL database | One external scheduler calling the authenticated jobs endpoint |

Next.js loads process variables first, then `.env.$NODE_ENV.local`, `.env.local` (except in test mode), `.env.$NODE_ENV`, and `.env`. Keep machine-specific values out of shared templates. For an isolated test server, export **every** value in the test template so a private `.env.local` cannot supply live keys. Use separate development and production database/provider accounts. Never reuse the recovered local database for CI. Production rejects HTTP app URLs, missing/invalid PostgreSQL URLs and the in-process scheduler. Unit tests stub provider settings and make no real provider requests.

For a local production-build smoke test:

```sh
npm run build
npm start
```

For a disposable E2E run (stop any server on port 3000 first):

```sh
set -a
. ./config/environments/test.env.example
set +a
npm run build
npm start
# In another terminal: npm run test:e2e
```

No secrets are required for CI. The GitHub Actions workflow installs the lockfile, generates route types, type-checks, lints, runs unit tests, builds and runs Chromium browser/API tests. Its database exists only on the runner. `npm run typecheck` runs `next typegen` first, so it also works in a clean checkout.

Production configuration is validated, but CON-6 does not provision hosting, a managed database or a production scheduler, and does not assert that the public-launch gates above are complete.

## Local storage and recovery

Keep the checkout downloaded if it is inside iCloud/Documents. Before running builds or opening PGlite, confirm that required files are physically available; placeholders can cause reads to time out. Store a live database outside cloud synchronization via an absolute `LOCAL_DATABASE_PATH`. Stop all app/database processes, make a byte-verified backup, copy the entire existing database including empty directories, verify it opens, and only then change that path. Never reset a database to work around missing files. Do not run two processes against one PGlite directory.

This Mac's existing application and database were recovered without replacing data. A protected backup and a separate local runtime database are outside the repository; machine-specific paths stay in ignored `.env.local`. Installed dependencies use a local `node_modules` symlink on this machine; it is ignored and not required by a fresh clone.

## Local automatic checks

Set `AUTO_CONCERT_CHECKS=true` and restart. On a single-process local PGlite server, a check runs 15 seconds after startup and every five minutes afterward. Newly followed live artists are picked up on the next check; successful artist results are reused for an hour across accounts, failed checks back off for 15 minutes. Manual and scheduled imports are serialized, overlapping job runs coalesce, and failed accounts do not block other accounts. Cached listings remain available during provider failures. Last attempt/success is shown per followed live artist in Settings. The visible app refreshes its inbox once a minute and when brought back to the foreground.

Checks stop when the server stops or the computer sleeps and resume on the next timer tick after waking. This local timer is disabled on Vercel or when `DATABASE_URL` is configured; use the authenticated `/api/jobs` route with a centrally scheduled worker for deployment.

### Scheduled checks on Vercel (CON-34)

`vercel.json` schedules a daily Vercel Cron call to `GET /api/jobs` at `0 5 * * *` UTC. The Hobby plan allows one cron per day, triggered anywhere within that hour; Pro allows more frequent schedules. Set a long random `CRON_SECRET` in the Vercel project's Production environment. Vercel then sends `Authorization: Bearer <CRON_SECRET>`, and requests without that exact token get `401`. `POST /api/jobs` with the same header still works for external schedulers. Each run imports followed live artists (with the existing per-artist cache and failure backoff), evaluates alerts and removes expired sessions, OAuth attempts, analytics and rate-limit rows. To check that a run happened, look at the Vercel project's Cron Jobs / Logs, and at the per-artist "last checked" times in Settings. Do not enable the timer during builds or browser tests. Important alerts include home-city shows, favourites, must-see matches and upcoming sales; Off generates no new alerts. A unique user/event/kind key prevents repeat alerts, while a sale reminder is intentionally separate from a discovery alert.
